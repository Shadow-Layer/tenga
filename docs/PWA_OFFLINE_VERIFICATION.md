# PWA and offline inventory verification

The frontend registers a small app-shell service worker and a web manifest. It caches only the public SPA shell and same-origin versioned static assets. It does not intercept `/api/*`, other cross-origin API hosts, or non-GET requests. The worker does not use Background Sync and never replays mutations. Authenticated API calls and inventory writes are handled by the open, authenticated application; an offline inventory write is persisted to IndexedDB before the UI reports that it was saved.

## Manual browser check

1. Build and serve the production frontend over HTTPS (or `localhost`), sign in, open **Stock operations** once, and open the assigned POS till while online. This stores tenant-scoped inventory choices, checkout product/tax snapshots, and the last verified open till session in IndexedDB.
2. In DevTools → Application, confirm the manifest, active `sw.js`, `tenga-app-shell-v1` cache, and `tenga-offline-operations` IndexedDB database.
3. Use DevTools → Network → Offline, reload the app, and confirm the shell opens. Confirm API-backed stock, movement history, and reports are identified as unavailable rather than shown as fresh authoritative data. The POS may use the last verified till session and cached product/tax data only to stage cash checkout; the server must confirm the session and sale after reconnection.
4. Record a receipt, issue, adjustment, count observation, or manager transfer. Confirm the UI reports **Saved on this device / Pending**, shows it in the operation queue, and labels any local balance effect provisional. Check that the event remains in IndexedDB after closing/reopening the tab.
5. In DevTools → Application → Cache Storage, verify the cache contains only the app shell/manifest/icon and static `/assets/*` files. No `/api/*`, login, stock, sale, or user response may appear there.
6. With a cached cart/catalog and assigned open session, stage a cash sale while offline. Verify it is explicitly unconfirmed, survives reload in `tenga-pending-cash-sales-v1`, and blocks another sale. Do not treat it as completed or issue goods based on a local-only result. Paynow is unavailable offline.
7. Restore connectivity. Confirm the authenticated app syncs queued inventory operations and displays per-operation applied, retryable, terminal, or reconciliation-required state. Retry the exact saved cash request and verify the same idempotency key and session are used; the server must reject a stale/closed/unassigned session without creating a sale. For a count, review the server's read-only current draft, then explicitly post the differences as a manager. Reconciliation sends the reviewed observations back as a snapshot; if they changed meanwhile, the server returns a conflict and requires a fresh review.
8. Force a sync transport failure and retry from the app. Verify that the same operation ID remains and that no operation disappears from the local queue.

The service worker can make the shell reopen offline; it does not cache or replay authenticated API requests. Inventory and cash-sale writes are stored by the application in IndexedDB with separate stable identities. Offline balances and cash sales remain provisional until server acknowledgements; sales additionally require the original session, operator, organization, price, and tax data to remain valid. Returns are not supported in this release.
